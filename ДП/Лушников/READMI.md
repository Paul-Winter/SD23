План разработки веб-платформы для онлайн-продаж (Маркетплейс) с мультимодальной доставкой для регионов тундры и Крайнего Севера
Выбор технологического стека (Рекомендация)
Среда разработки: Visual Studio (2026 Community).

Язык и фреймворк: C# / ASP.NET Core MVC или ASP.NET Core Web API (с разделением на backend и frontend).

База данных: MS SQL Server (отлично интегрируется с Visual Studio) или PostgreSQL.

ORM: Entity Framework Core (EF Core) для работы с базой данных.

Frontend: HTML, CSS, JavaScript, Bootstrap (для быстрого прототипирования) или React/Vue (если захотите сделать SPA).

Архитектура: MVC (Model-View-Controller) или Чистая архитектура (Clean Architecture) для масштабируемости.

Дополнительно для логистики: SignalR (телеметрия и чат диспетчера), интеграция с погодными API, интеграция с «ЭРА-ГЛОНАСС» (для БАС).

Этап 1: Аналитика и проектирование (Фундамент)
1.1. Определение ролей пользователей
Покупатель: ищет товары, добавляет в корзину, оформляет заказ, выбирает способ доставки (наземная / воздушная БАС / комбинированная), пишет отзывы.

Продавец: создает магазин, добавляет/редактирует товары, управляет заказами, смотрит статистику, указывает габариты и вес товара (критично для расчёта возможности доставки БАС).

Администратор: банит пользователей, модерирует товары, управляет категориями, решает споры, настраивает маршруты и зоны доставки.

Оператор БАС (беспилотных авиационных систем): планирует полётные задания с учётом погоды и рельефа, проводит предполётную подготовку дрона, управляет полётом в ручном или автоматическом режиме, действует при потере связи и нештатных ситуациях.

Диспетчер логистики: координирует наземные и воздушные маршруты, подтверждает вылеты при пограничных погодных условиях, управляет очередью доставок.

Водитель/курьер наземной доставки: выполняет доставку в населённые пункты, доступные наземным транспортом (включая зимники и сезонные дороги).

1.2. Определение целевых регионов (на основе реальной статистики)
Маркетплейс с мультимодальной доставкой имеет смысл только там, где наземная логистика либо отсутствует, либо сезонно парализована. Ключевой критерий — доля населённых пунктов без круглогодичной дорожной связи.

Республика Саха (Якутия): в республике 641 населённый пункт (13 городов, 41 посёлок городского типа, 582 сельских населённых пункта). Из них 248 населённых пунктов не имеют связи по дорогам с твёрдым покрытием с сетью дорог общего пользования — почти 39% всех населённых пунктов находятся в зоне, где воздушная доставка становится критически важной, а наземная возможна только сезонно (зимники).

Чукотский автономный округ: из 46 населённых пунктов около 67% имеют численность населения менее 500 человек. Плотность населения — 0,07 чел/км². При такой рассредоточенности содержание наземной инфраструктуры экономически нецелесообразно.

Что добавить в план: сформировать таблицу «Регион → Количество населённых пунктов → Из них без круглогодичных дорог → С населением менее 500 чел → Доступность наземной доставки (круглогодично / сезонно / только зимник) → Приоритет для БАС». Это станет основой для выбора пилотных зон и распределения способов доставки.

1.3. Мультимодальная модель доставки (наземная + воздушная)
Ключевой принцип: доставка не обязана быть только воздушной. В регионах тундры и Крайнего Севера должна быть предусмотрена наземная доставка — как основной способ там, где есть круглогодичный доступ, и как сезонный (зимники) там, где доступ есть только зимой.

Типы доставки, которые должна поддерживать платформа:

Наземная круглогодичная — применяется для населённых пунктов с дорогами с твёрдым покрытием; ограничения только погодные.

Наземная сезонная (зимники) — применяется для населённых пунктов, доступных только зимой; ограничения: только в сезон действия зимника, весогабаритные ограничения.

Воздушная БАС (самолётного типа) — применяется для дальних маршрутов и населённых пунктов без дорог; ограничения: погода, дальность, необходимость площадки для взлёта/посадки.

Воздушная БАС (вертолётного/мультироторного типа) — применяется для точной доставки в населённый пункт без инфраструктуры; ограничения: погода, малая дальность, малый вес груза.

Комбинированная — наземный участок до точки взлёта, затем БАС до конечного пункта; ограничения: комбинация ограничений обоих типов.

Логика выбора способа доставки: система автоматически определяет доступные способы для конкретного населённого пункта назначения на основе справочника маршрутов и текущих условий (сезон, погода, статус зимника). Покупатель видит только те варианты, которые реально доступны.

1.4. Проектирование базы данных (ER-диаграмма)
Базовые таблицы: Users, Roles, Shops, Categories, Products, ProductImages, Orders, OrderItems, Reviews, Payments.

Таблицы для мультимодальной логистики:

DeliveryMethods (способы доставки: наземная круглогодичная, наземная сезонная, БАС самолётная, БАС вертолётная, комбинированная).

DeliveryZones (населённые пункты, обслуживаемые платформой, с указанием доступных способов доставки и частоты рейсов).

GroundRoutes (наземные маршруты: точки отправления/назначения, тип дороги, сезонность, ограничения по весу/габаритам).

WinterRoads (зимники: период действия, статус открытия/закрытия, грузоподъёмность).

DroneRoutes (маршруты БАС: точки взлёта/посадки, расстояние, ограничения по погоде).

DroneFlights (конкретные полёты: оператор, дрон, статус, погодные условия в момент вылета).

WeatherRestrictions (пороговые значения: ветер, видимость, температура — при которых вылет/выезд запрещён).

DeliveryOperators (операторы БАС и диспетчеры: квалификация, привязка к маршрутам).

DeliveryStatusHistory (история статусов заказа с указанием способа доставки на каждом этапе).

Продумать связи (один-ко-многим, многие-ко-многим).

1.5. Создание макетов (UI/UX)
Нарисовать в Figma или на бумаге: главную страницу; карточку товара; корзину; личный кабинет покупателя (с выбором способа доставки и отображением доступных вариантов для его населённого пункта); личный кабинет продавца; панель диспетчера логистики (карта маршрутов, очередь доставок, погодные условия); панель оператора БАС (полётные задания, статус дронов).

Этап 3: Разработка Backend (Серверная часть)
3.1. Модели данных (Models)
Создать C# классы, описывающие таблицы БД (User, Product, Order, DeliveryMethod, DeliveryZone, GroundRoute, WinterRoad, DroneRoute, DroneFlight и т.д.).

3.2. Контекст базы данных (DbContext)
Настроить EF Core для работы с моделями.

3.3. Миграции
Создать базу данных на основе моделей (Add-Migration → Update-Database).

3.4. Сервисы (Services)
ProductService — поиск товаров, фильтрация.

OrderService — оформление заказа с выбором способа доставки.

DeliveryRouterService — ключевой сервис: определяет доступные способы доставки для конкретного населённого пункта с учётом сезона, погоды и статуса дорог.

GroundLogisticsService — расчёт наземных маршрутов, проверка статуса зимников, весогабаритный контроль.

DroneLogisticsService — проверка погодных условий перед вылетом, расчёт дальности и выбор точки дозаправки/пересадки, интеграция с «ЭРА-ГЛОНАСС».

OperatorService — привязка оператора к дрону и маршруту, валидация квалификации, журнал полётов.

WeatherService — интеграция с погодными API, сравнение с пороговыми значениями для каждого типа доставки.

Ключевая логика DroneLogisticsService: проверка погодных условий перед вылетом (если ветер превышает допустимый для конкретной модели дрона, полёт откладывается, заказ переводится в статус «Ожидание погоды», покупатель получает уведомление); расчёт дальности и выбор точки дозаправки/пересадки для маршрутов протяжённостью 20/50/100 км (такие рассматриваются в пилотном проекте Минтранса); интеграция с «ЭРА-ГЛОНАСС» (с 1 октября 2026 года подключение к системе — обязательное условие для подачи плана полёта; если у оператора нет активного личного кабинета, план отклоняется).

Ключевая логика GroundLogisticsService: проверка статуса зимника (открыт/закрыт, грузоподъёмность); сезонное планирование (если зимник закрыт, система предлагает альтернативу — БАС или комбинированную доставку); весогабаритный контроль для наземного транспорта.

3.5. Контроллеры (Controllers)
Написать API-эндпоинты или методы для обработки запросов от пользователей (например, GET /api/products, POST /api/orders, GET /api/delivery-methods?settlementId=..., POST /api/drone-flights).

Этап 5: Ключевой функционал (MVP — Минимально жизнеспособный продукт)
Что должно работать в первую очередь:

Регистрация и вход (разделение на покупателей, продавцов, операторов БАС, диспетчеров логистики).

Возможность продавца добавлять товар (название, цена, фото, описание, вес, габариты).

Отображение товаров в общем каталоге.

Справочник населённых пунктов и доступных способов доставки (наземная круглогодичная, наземная сезонная, БАС, комбинированная).

Корзина и оформление заказа с выбором способа доставки из доступных для конкретного населённого пункта (пока можно без реальной оплаты, просто смена статуса заказа).

Статусная модель заказа: «Ожидает погоды» → «Запланирован полёт/рейс» → «В пути» → «Доставлен» / «Возврат».

Базовая система поиска.

Создание маршрута доставки администратором: населённый пункт отправления → населённый пункт назначения → способ доставки → ограничения (погодные, сезонные, весогабаритные).

Уведомление покупателя при изменении статуса (email или push).

Интеграция с погодными API для автоматического пересчёта ETA и блокировки вылетов/выездов.

Панель диспетчера БАС: карта с дронами в реальном времени (через телеметрию), очередь полётов, ручное подтверждение вылета при пограничных погодных условиях.

Автоматический выбор типа дрона: самолётного типа — для дальних маршрутов (большая дальность, но требует площадки для взлёта/посадки); вертолётного/мультироторного — для точной доставки в населённый пункт без инфраструктуры.

Страхование груза и парашютные системы — обязательные элементы реальных дрон-доставок.

Интеграция с «ЭРА-ГЛОНАСС» для подачи планов полётов.

Мониторинг зимников: интеграция с дорожными службами для отслеживания статуса открытия/закрытия сезонных дорог.

Комбинированные маршруты: автоматическое построение цепочки «наземный участок → точка взлёта БАС → воздушный участок → конечный пункт».

Этап 7: Тестирование и Развертывание (Deployment)
Тестирование: написать Unit-тесты для ключевых сервисов (xUnit или NUnit), особенно для DeliveryRouterService, DroneLogisticsService и GroundLogisticsService. Проверить безопасность (защита от SQL-инъекций, XSS, CSRF).

Хостинг: арендовать сервер (VPS) или использовать облачные сервисы (Azure, Yandex Cloud). Базу данных разместить там же.

Публикация: настроить CI/CD (например, через GitHub Actions) для автоматической сборки и выгрузки проекта на сервер при обновлении кода.

Этап 8: Юридическое сопровождение и регуляторика (критически важно)
Беспилотная доставка в России регулируется жёстче, чем может показаться на этапе прототипирования:

Полёты гражданских дронов тяжелее 250 г требуют подключения к «ЭРА-ГЛОНАСС» и активного личного кабинета.

Выделено отдельное воздушное пространство H с максимальной высотой 150 м и скоростью до 450 км/ч.

Пилотный проект Минтранса по грузовым дронам рассчитан до конца 2027 года и пока охватывает до 5 регионов; итоги отбора планировались в ноябре. Это значит, что для маркетплейса нужно либо попасть в число пилотных зон, либо строить MVP в режиме экспериментального правового режима.

Необходимо получить разрешения на полёты в выбранных регионах, а также согласовать наземную доставку по зимникам с дорожными службами.

Включить в план отдельный пункт: «Юридическое сопровождение и получение разрешений на полёты в выбранных регионах» — без этого техническая часть не имеет значения.

Сводная логика мультимодальной доставки
Наземная круглогодичная доставка применяется для населённых пунктов с дорогами с твёрдым покрытием; ограничения — погодные условия; ответственный — водитель/курьер.

Наземная сезонная доставка (зимники) применяется для населённых пунктов, доступных только зимой; ограничения — сезон, грузоподъёмность зимника; ответственный — водитель/курьер.

БАС самолётного типа применяется для дальних маршрутов и населённых пунктов без дорог; ограничения — погода, дальность, площадка для взлёта/посадки; ответственный — оператор БАС.

БАС вертолётного/мультироторного типа применяется для точной доставки в населённый пункт без инфраструктуры; ограничения — погода, малая дальность, малый вес груза; ответственный — оператор БАС.

Комбинированная доставка применяется, когда наземный участок до точки взлёта сочетается с БАС до конечного пункта; ограничения — комбинация ограничений; ответственные — диспетчер логистики и оператор БАС.
